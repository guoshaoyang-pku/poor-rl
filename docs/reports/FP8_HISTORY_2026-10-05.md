# FP8 历史探针核对（2026-10-05）

此前 trainer 探针测试的是 **BF16 base＋FP8 计算＋LoRA**。base 冻结，只有 adapter 更新；它没有测试 FP32 主参数、FP8 full FT 与共同训推前向。

## 找到的原始结果

`trainer_bench_v3.py` 与 `bench_v3.json` 来自参考部署 360-1 的 `/tmp/`。同为 16,384 tokens/step；下表直接抄录 JSON。

| 路径 | 秒/步 | token/s | 峰值显存 GiB | 原记录 MFU |
|---|---:|---:|---:|---:|
| BF16 full FT | 0.5936 | 27,599.2 | 35.71 | 14.3% |
| BF16 base＋LoRA | 0.8290 | 19,763.2 | 32.93 | 6.9% |
| FP8 base＋LoRA | 1.3463 | 12,169.5 | 55.96 | 2.1% |

MFU 是旧脚本的估计：`(4 × base参数量 + 2 × 可训练参数量) × tokens / 时间 / 理论峰值`；BF16/FP8 分母分别为 989/1,979 TFLOP/s。未逐算子计数，不能直接用于当前 RL 总吞吐或混合精度利用率比较。

## 源码确认的差异

- base 用 BF16 加载，FP8 用 `torchao.float8` 的 tensorwise recipe；没有 FP32 full FT 主权重方案。
- loss 先生成整段完整词表 logits 再执行 cross entropy；没有当前的 shared prefix 与 chunked logprob 路径。
- 找到的代码没有 `torch.compile`。采集当天安装的 torchao 0.18.0 backward 不检查 `ctx.needs_input_grad`，即使 base 冻结也计算 wgrad；eager scale 路径另行做 abs、amax 和 FP64 scale。
- 旧文档的 8k-token `22,001 / 41,715 = 0.53×` 混用了 FP8 LoRA 和 BF16 full FT。相同 LoRA 的文档数字是 `22,001 / 30,983 = 0.71×`；该 8k 原始 JSON 尚未找到。
- `812 ms / 121 ms = 6.7×` 没有找到绑定源码哈希的原始 trace，不能据此归因到具体 kernel，也不能推出 Hopper FP8 training 不可行。
