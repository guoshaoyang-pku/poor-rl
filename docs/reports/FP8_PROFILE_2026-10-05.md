# H200 FP8 profiling（2026-10-05）

主要 policy Linear 和 LM head 的前向、dgrad、wgrad 已执行原生 FP8。当前耗时最多的是逐元素计算、归约和拷贝；FP32 Adam 更新占比很小。增加实际 MLP microbatch 的两个实现均未获得显著加速。

数据来自公开源码 `ed2116b`，核心文件 SHA-256 与远端逐一匹配。这是单 H200 的算子和训练 microbatch 探针，不是 4+4 或 4+4+n 的总 RL 吞吐。训练探针使用最终 FP8 源码、同一 checkpoint、G32、梯度累计 1；历史 completion 被放在共同 prompt 下，原始配对不可恢复，因此是形状与隔离测试。

## 实际 FP8 覆盖

| 执行部分 | GEMM 次数 | 输入精度 | 输出精度 | 部分矩阵运算量 TFLOPs |
|---|---:|---|---|---:|
| policy 初次前向 | 744 | E4M3 / E4M3 | BF16 | 94.289 |
| backward 中的 checkpoint 与 logits 重算 | 428 | E4M3 / E4M3 | BF16 | 53.975 |
| policy dgrad + wgrad | 1,480 | E5M2 / E4M3 | FP32 | 188.423 |
| 合计 | 2,652 | FP8 | — | 336.686 |

动态 dtype 记录与 2,652 个原生 FP8 kernel 数量一致，包含 LM head 的前向、logits 重建、dgrad 和 wgrad。主参数、累加梯度、Adam moments 均为 FP32；反向 GEMM 的 FP32 输出是累加结果，输入仍为 FP8。

rollout 探针发现 96 个融合后的 FP8 projection 模块及 FP8 head，实际执行 3,201 个 SM90 FP8 GEMM kernel。权重/head cache 的量化 bytes 与 scales、激活量化对 batch 拼接的独立性，共 6 项检查通过。探针为 eager、8 请求各生成 32 token，不能代表生产 CUDA graph 吞吐。

norm、GDN、attention、softmax 等仍按两端各自前向规则使用 BF16/FP32，没有给 trainer 单独增加精度。相同量化规则不能证明整模型一致：既有 LR=0 训推 log-ratio P90 为 0.014004，超过 0.004 gate，仍未通过；GDN chunk 与 sequential decode 的数值对齐需要继续修复。

此表按 37,191 个 kernel 时长求和；CPU launch 关联覆盖 100%，分类规则含启发式，其他项保留。无 profiler 的 CUDA event 中位数为：训练 compute 2,362.47 ms、clip 3.94 ms、fused Adam 6.51 ms。clip + Adam 约为单次 compute 的 0.44%；不应将该单 microbatch 比例直接当作生产 step 比例。

冻结 BF16 reference 前向占 570.51 ms（24.83% kernel 时间），已包含在表中。134.11 ms BF16 GEMM 中，127.51 ms 属于 reference；policy 前向与 backward 仅为 1.78 / 4.82 ms。reference 是 KL anchor，将它改成 FP8 会改变训练目标，需要单独对照。

权重量化 cache 在 Adam hook 执行后刷新：初次前向有 142 次 FP32 主权重转置量化，backward / checkpoint 中为 0 次。量化总时间仍是 122.96 ms，不能把嵌套 scope 的不完整归因误读成零量化开销。

此处为 top-300 phase/op 记录中的具体归因，已包含在上表，不能再次相加。FP32 主权重的量化副本按 optimizer update 缓存；每层／tile 的激活、反向梯度、norm 临时量和布局仍需反复读写。只优化 head 的 FP32 add 或 dx cast，单独收益上限很小。

## 增加实际 microbatch

所有对照都保持两组 G32、共 64 个序列、梯度累计 1。合并的是 tokenwise norm/MLP，attention/GDN 仍保留各组 prefix 和 state，head tile 边界保留。表中 n=3，为固定输入的前反向中位数。

| 对照 | 前反向 ms | 峰值 GiB | 每组 checkpoint 层数 |
|---|---:|---:|---|
| 跨两组合并的串行基线 | 4,948.42 | 119.85 | 9 / 10 |
| 跨两组合并，M=135,723 | 5,305.84 | 121.31 | 17 / 17 |
| 跨两组合并，减少 checkpoint | OOM | — | 16 / 16 |
| 较早的跨两组合并测量 | 5,360.00 | 104.10 | 18 / 18 |
| 组内合并的串行基线 | 4,941.91 | 119.85 | 9 / 10 |
| 各组内合并，M=65,053 / 70,670 | 4,932.71 | 125.18 | 9 / 10 |

跨两组合并慢 7.22%，显存压力使重算增加；较早 18 层版本相对它自己的 4,943.22 ms 基线慢 8.43%。各组内合并只快 0.186%，显存增加 5.325 GiB，保持原来的 checkpoint 层数。两个 prototype 均未接入生产。

各组内合并后 logprob 逐位相同，loss 差为 0；抽查梯度 cosine 0.997144–0.999305，相对 L2 差 3.730–7.597%。反向 tensorwise FP8 scale 随合并改变，且没有 serial-repeat 梯度控制，不能将全部差异归因于 scale。非零 Adam 更新后，主参数与 moments 均为有限 FP32，抽查主权重确实更新。这些检查没有替代训推一致性 gate。

## MFU 与后续优化

完整混合精度 MFU 暂未测得。336.686 TFLOPs 仅按实际 projection/head GEMM 的 2MNK 统计，包含 padding、checkpoint 与 head logits 重算；未计 reference、GDN、attention 等计算，也不是完整的有效模型 FLOPs。该工作量除以 260.39 ms FP8 kernel 时间，得到约 **1,293 TFLOP/s**；按 [H200 规格](https://www.nvidia.com/en-us/data-center/h200/)的 dense FP8 峰值 1,979 TFLOP/s 算约 65.3%。这是局部 GEMM 执行效率，包含重算，不能写成模型 MFU。以本次 kernel 占比计算，FP8 GEMM 再快一倍，整段 kernel 的理想加速也只有约 6.0%；该上限不包含排队、同步等端到端变化。

## 避免 GDN 整段拼接的实测

独立 tail 卷积避免完整输入 cat/pad，保留 BF16 tap-product 舍入、FP32 顺序求和、eager SiLU 和 prefix 梯度。仅改变 policy 数据布局，reference 保持原样。下表为同一 G32／58,248 completion tokens 的前反向，梯度累计 1；不包括 optimizer、DDP 和 rollout。

| 路径 | 前反向 ms | 峰值 GiB | checkpoint |
|---|---:|---:|---:|
| 原路径，ABAB 两轮中位数 n=6 | 2,360.76 | 117.75 | 9 |
| 独立 tail，ABAB 两轮中位数 n=6 | 2,406.05 | 109.16 | 9 |
| 降 checkpoint 的对照 n=3 | 2,354.08 | 116.94 | 9 |
| 独立 tail，降 checkpoint n=3 | 2,373.44 | 114.95 | 8 |
| 独立 tail，再降 checkpoint n=3 | 2,365.03 | 119.89 | 7 |

24 个 CPU case 的前向和全部梯度逐位一致。CUDA 小型卷积前向／输入／tail 梯度一致；真实形状卷积 wgrad 相对 L2 差 1.65e-5，来自归约变化。完整模型所有 arm 的 logprob／loss 逐位一致，梯度全为有限 FP32；抽查梯度 cosine ≥0.999988，原路径重复运行同样有差异。真实 FP32 Adam 更新与 moments 检查通过。该候选省显存但未获得提速，未推广；上述前向检查仍未替代 train/decode gate。

后续优先融合布局与归约临时量。冻结 BF16 reference 占 24.83%，4+4+n 可测试额外 reference worker 分担其前向，保持 KL anchor 不变；这仍是待测方案。GDN chunk／decode 需要共享数值规则，整模型 train/decode gate 通过后，再比较完整总 completion token/s。
